# Отказоустойчивый мультиплеер (RESILIENT 1–5)

Дата: 2026-11-12 · Компоненты: `net/net_session.gd`, `net/net_config.gd`, `net/rtc_link.gd`,
`net/server/signal_server.gd`, `dev/mp_resilience_test.gd`

## Проблема

Мультиплеер был «очень сломанный»: постоянные фризы и паузы на синхронизацию. Разбор показал
четыре источника стопов и один фатальный дефект транспорта.

| # | Источник | Как проявлялся |
|---|---|---|
| 1 | Любой ресинк (рассинхрон хеша / возврат игрока) **останавливал матч целиком**: хост не выпускал ходы, пока пир восстанавливал мир (`_sync_wait`), до 25 с на каждого | «СИНХРОНИЗАЦИЯ С ИГРОКОМ...» на весь матч |
| 2 | Пороги удержания были жёсткими: `HOLD_SLOW=15` ходов (1.5 с), `HOLD_BACKLOG=25` (2.5 с). Любой х hitch гостя длиннее 1.5 с замедлял матч вдвое, длиннее 2.5 с — останавливал | «ЖДЁМ X · МЕДЛЕННОЕ УСТРОЙСТВО» постоянно |
| 3 | Одно несовпадение хеша сразу отправляло полный снапшот мира | ресинки по ерунде |
| 4 | Снапшот уходил одним залпом надёжных пакетов по 32 КиБ | затык канала → ходы стоят в очереди → ещё больший backlog |
| 5 | Гость, отставший больше чем на историю ходов (900 ходов), вечно висел в «ЖДЁМ ХОСТ...» до 45-секундного переподключения | «кирпич» без пути назад |
| 6 | **Relay-транспорт (онлайн-матчи через сервер): при «turn» клиент закрывал сокет, на котором жил туннель матча** | старт-пакет и ходы молча терялись — матч не начинался/вис |

## Решения

### RESILIENT 1 — матч больше не встаёт на время ресинка
Хост продолжает выпускать ходы, пока пир восстанавливает снапшот: пир переигрывает историю
ходов из буфера `turns` (хранится 900 ходов = 90 с). Матч встаёт только если окно переигрывания
вот-вот кончится (`TURN_KEEP − TURN_MARGIN`, маржа 120 ходов) — то есть практически никогда:
восстановление дольше 78 с само по себе провал по watchdog'ам. `_sync_wait` теперь только
учитывает пиры, а не тормозит всех.

### RESILIENT 2 — плавное замедление вместо ступеней
Пороги подняты: `HOLD_SLOW=30` (3 с), `HOLD_BACKLOG=60` (6 с), `HOLD_MAX=90`. Вместо жёсткого
скачка в x0.5 — плавная кривая: `x1.0 → x0.3` по мере роста отставания. Короткий хич гостя
теперь стоит немного темпа, а не видимой паузы.

### RESILIENT 3 — снапшот течёт потоком, не залпом
`_resync_tick` (вызывается из `_process` хоста, работает даже когда ходы удержаны — именно
тогда снапшот нужнее всего) стримит не больше `SNAP_PARTS_PER_TURN=12` чанков по 32 КиБ за
0.1 с игрового времени (~3.8 МБ/с, токен-ведро ×3 на bursts). Ходы не застревают за снапшотом.

### RESILIENT 4 — двухступенчатое подтверждение рассинхрона
Первое несовпадение хеша только фиксируется (`_suspect`); снапшот уходит после **второго
подряд** несовпадения того же пира (`RESYNC_CONFIRM=true`). Случайные расхождения (запись в
симуляцию из UI на одном устройстве, краевой случай округления) заживают молча.

### RESILIENT 5 — самоспасение гостя
Гость, чья история переигрывания кончилась (`last_turn − exec_turn > TURN_KEEP − 32`), сам
просит у хоста снапшот (`_resync_rq`, повтор раз в 10 с) вместо вечного «ЖДЁМ ХОСТ...» и
45-секундного переподключения. Хост ставит пир в очередь снапшотов, минуя кулдаун.

### RESILIENT 6 (транспорт) — relay-матч живёт на своём сокете
В relay-режиме (сервер сигналов + WebSocket-туннель, без WebRTC) обработчик «turn» больше не
закрывает сокет: туннель матча живёт на нём. Дополнительно:

- **Самохостинг локального relay**: `signal_url` вида `ws://127.0.0.1`, `ws://localhost`,
  `ws://192.168.*`, `ws://10.*`, `ws://172.16–31.*` распознаётся как relay-режим — WebRTC и
  **аккаунты не нужны** (свой сервер → свои правила). Имя игрока — локальный ник.
- **`--open` у сигнального сервера**: dev-режим без регистрации (только для локальных/CI стендов).

## Догон при отставании

При отставании ≥3 ходов кадр может потратить на симуляцию до `CATCHUP_MS=60` мс (было плоские
14 мс — при тяжёлом тике гость выдавал 1 тик за кадр и никогда не догонял, матч «держали»
вечно). Бюджет ограничен, кадр дышит; на быстрой симуляции тики просто выполняются все.

## Тест

```bash
# 1. сигнальный сервер (локальный, без аккаунтов)
godot --headless --path . -s net/server/signal_server.gd -- --port=19090 --bind=127.0.0.1 --open

# 2. signal_url=ws://127.0.0.1:19090/mp/signal в user://net.cfg, затем два инстанса:
godot --headless --path . --mp-resilience=relay-host
godot --headless --path . --mp-resilience=relay-guest
```

Референсный прогон (Godot 4.7.2 headless, x8 скорости симуляции, ~2100 ходов, LAN-класс канала):

```
[MP-RES] RESULT relay-host:  go=true exec=2167 last=2166 behind=-1 stall_max=8.4 holds=10 resyncs=0 desyncs=0 asks=0 tick_ms=0.9
[MP-RES] RESULT relay-guest: go=true exec=2150 last=2151 behind=1  stall_max=7.5 holds=7  resyncs=0 desyncs=0 asks=0 tick_ms=1.5
[MP-RES] PASS relay-host
[MP-RES] PASS relay-guest
```

`stall_max` — момент сборки мира гостем (тяжёлые тики ~258 мс), поглощённый RESILIENT 2/догоном
без остановки матча: хост ни разу не встал, конечное отставание гостя — 1 ход.
