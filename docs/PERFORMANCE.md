# PERFORMANCE.md — инженерный отчёт по оптимизации v1.0

Документ фиксирует узкие места, найденные профилированием, применённые исправления и
измеренный эффект. Все числа получены на встроенном headless-бенчмарке самой игры —
воспроизвести можно одной командой:

```bash
BENCH_UNITS=250 BENCH_GAME_S=120 godot --headless --path . -- --bench
```

## 1. Методика

- Мир 256×256, 4–5 стран, ~250 юнитов на страну (1000–1250 юнитов), сценарий «все со всеми»
  + рейдовые группы у чужих баз — максимальная нагрузка на бой и «вывод войск».
- Симуляция тикает шагами по 0.2 игровых секунды (5 тиков/с при 1×), бюджет кадра — 12 мс,
  но один тяжёлый шаг превышает бюджет целиком.
- Профайлер: `GameWorld.perf_sys` (максимальное время подсистемы за шаг) + PERF PROBE.

## 2. Профиль ДО оптимизаций

Пик боя (первая минута, максимальная плотность юнитов):

```text
frame_ms = 285.4  (≈ 3.5 FPS только на симуляции)
  ops.update   = 146.27 мс   ← главный виновник
    wd_tick    = 142.10 мс   ← 97% ops.update
  army.update  =  56.52 мс
  aftermath    =   2.52 мс
  ai.update    =   2.28 мс
```

### Корневые причины

| # | Место | Проблема | Стоимость |
|---|---|---|---|
| 1 | `operations.gd :: wd_exit` | Спиральный скан до 320² ячеек на каждый вызов; вызывается на каждую казарму и каждого «беспризорного» юнита за `_wd_tick` | O(r²) за вызов |
| 2 | `operations.gd :: wd_units` | Полный скан всех юнитов с `_owner_at` на каждый ключ вывода войск | O(ключи × юниты) |
| 3 | `operations.gd :: _queued` | Линейный проход очереди приказов, вызывается **на каждого юнита** за `_wd_tick` | O(юниты × очередь) |
| 4 | `operations.gd :: _centre` | Квадратичный перебор пар юнитов для поиска плотного кластера | O(n²) на вызов |
| 5 | `operations.gd :: _ai` (артподготовка) | Подсчёт «соседей» для каждой замеченной цели полным перебором всех замеченных | O(n²) |
| 6 | `army.gd :: _acquire` | Поиск цели для каждого юнита каждые 0.25 с, включая юнитов, уже ведущих бой | O(юниты × сетка) |
| 7 | `project.godot` | Mobile-рендер + D3D12 на ПК: тяжёлый драйверный путь для 2D-игры | GPU/драйвер |

## 3. Применённые исправления

### 3.1 `wd_exit` — мемоизация выхода к границе

Результат поиска выхода к границе кэшируется по бакетам 64px на 12 игровых секунд
(`_wd_exit_c`). Спираль запускается один раз на бакет вместо одного раза на юнит/казарму.
Конечная точка перед отправкой юнита всё равно перепроверяется `_wd_legal`, поэтому
поведение (легальность прохода) не меняется.

### 3.2 `_wd_tick` — конвейер

- Юниты группируются по странам **одним проходом** (`by_c`), выборка «чужой земли» идёт
  только по бакету своей страны (`_wd_units_b`).
- Очередь приказов `_oq` сворачивается в набор id за O(1) (`qfids`).
- Ключи вывода войск обрабатываются порциями `WD_KEYS_PER_TICK = 2` с ротацией курсора —
  стоимость распределяется между тиками вместо пика раз в 2 игровые секунды.

### 3.3 `_centre` — якорная кластеризация за O(n)

Якорь выбирается как юнит, ближайший к центроиду армии; кластер — юниты в радиусе
`CLUSTER_R` от якоря. Результат практически идентичен выбору зоны максимальной плотности,
но без квадратичного перебора пар.

### 3.4 ИИ артиллерии — сетка 45px

Позиции замеченных целей кладутся в хеш-сетку 45px; плотность считается по 3×3 ячейкам
с **точной** проверкой `distance_squared < 45²` — семантика выбора цели сохранена,
стоимость снижена с O(n²) до O(n·k), где k — средняя плотность ячейки.

### 3.5 Стаггеринг `_acquire`

За один скан (0.25 c) цель ищет только половина юнитов (чётные/нечётные `u.id`, флаг
`_acq_flip`); каждый юнит ищет цель раз в 0.5 c. Юнит с валидной целью поиск не выполняет
вообще (короткое замыкание через `_valid`). На тактику это не влияет: время реакции +0.25 с
в худшем случае при шаге симуляции 0.2 с.

### 3.6 Рендер

`renderer/rendering_method` → `gl_compatibility` (Windows/macOS/desktop Linux):
для 2D-стратегии это самый лёгкий и совместимый бэкенд, особенно на встроенной графике
и старых драйверах. Драйвер устройства — Vulkan (используется только при переключении
метода обратно на Forward/Mobile).

### 3.7 Инструментация

`army.update` и `operations.update` размечены тонкими счётчиками (`_pf2`/`_pfv`, нулевая
цена без `perf_prof`): `_advance`, `_fight`, `_maybe_fpv`, снаряды, tac и т.д. — всё видно
в PERF PROBE и в отчёте бенчмарка.

## 5. Нативное ядро df_native (Rust, GDExtension) — v1.0.3–1.0.5

Потолок GDScript-интерпретатора обходится переносом «математики войны» в нативную
библиотеку `native/df_native` (godot-rust, api-4-7). Методика та же: снапшот живых
не-FPV юнитов + пространственная сетка 128px живут в Rust, GDScript передаёт позиции
и флаги, получает готовые решения и исполняет эффекты (fx/sfx/урон).

| Пасс | Что считает | Эффект |
|---|---|---|
| `acquire_one`/`valid_one` | поиск/перепроверка цели | поиск целей ×20, каждый юнит раз в 0.5 с |
| `spot_all` | разведка целиком (юниты+здания) | `fire:_spot` 3.5 мс → ~0.3 мс |
| `rockets_step`/`shells_step` | баллистика | O(n) в Rust |
| `aim_pick` | выбор арт-цели | ф32-паритет бокса |
| `occupy_candidates` | префильтр окопов | — |
| `fight_decide` (v1.0.5) | ядро боя: cd/роли/дым/подавление | юнит-цикл 34.7 → 25 мс |
| `wd_scan` (v1.0.5) | скан «вывода войск» | скан земли и пар в Rust, приказы в GDScript |
| `spot_density` (v1.0.5) | плотность целей арт-ИИ | O(n²)→O(n) в Rust |

Замер (BENCH_UNITS=250, сид 424242, пик боя 0 мин, натив vs чистый GDScript):

```text
frame_ms      156.1 → 143–149
army.update    53.2 → 42–44   (−17%)
army:units_loop 34.7 → 25.0   (−26%)
fire:_spot     3.49  → натив (в составе fire)
```

Паритет — побитовый (та же арифметика `Vector2` f32, идентичный `Hash32`): режим
`DF_WD_VERIFY=1` во время боя решает каждую ситуацию и GDScript-ом, и нативно;
расхождения печатаются как `[FIGHT-VERIFY]`/`[WD-VERIFY]`/`[DENS-VERIFY]` ошибки.
Базовая линия для A/B — `DF_NO_NATIVE=1`.

## 6. Известные остаточные затраты / план v1.1–1.2

- `_fight`-эффекты (fx/sfx/урон) и `_advance` остаются в GDScript — объектная связь;
  следующая ступень — многопоточные проходы по Packed-массивам (WorkerThreadPool).
- `aftermath.update` (3–5 мс) — троттлинг сканов до 0.5 с.
- Рендер: батчинг юнитов и LOD по зуму (units_layer), GPU-частицы вместо CPU.
- Экономика/дипломатия: инкрементальные пересчёты вместо полных проходов.

## 7. Правила для контрибьюторов

1. Любой PR с новой системой обязан прикладывать вывод `--bench` до/после.
2. Регресс > 5% среднего кадра на стресс-сцене — повод для отклонения PR.
3. Никаких полных сканов `gw.army.units` внутри тиковых систем: бакеты, индексы, сетки.
4. Никаких аллокаций (Array/Dictionary/лямбды) в горячих циклах — переиспользуемые
   контейнеры уровня класса.
5. Любое изменение нативного пасса сопровождается прогоном `DF_WD_VERIFY=1`
   (расхождений быть не должно) и синхронной правкой GDScript-эталона.
